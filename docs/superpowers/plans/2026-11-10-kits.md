# Kits de material e baixa por procedimento — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cadastrar kits de material e, ao concluir um tratamento, dar baixa no estoque. A baixa é confirmada pelo usuário, que pode ajustar os itens antes, e pode ser devolvida depois.

**Architecture:**
- **Banco:** uma migração SQL cria as tabelas de kits, as colunas novas e um gatilho que marca o tratamento concluído como `pendente`. Também cria as funções `treatment_material_apply/skip/return`. A função de baixa reaproveita `inventory_exit` da fase 1.
- **Servidor:** rotas Next no padrão `withClinic` + repo + `respostaDeErro`.
- **Telas:** a aba "Kits" no Estoque e a janela `ModalBaixaMaterial`, aberta pela ficha (aba Tratamentos) e pela evolução.

**Tech Stack:** Next.js 16.2.6 (App Router, Turbopack), Supabase/PostgREST, PL/pgSQL, React, Tailwind v4 (tokens tinta, linha, porcelana, petroleo, gengiva), vitest.

**Spec:** `docs/superpowers/specs/2026-11-10-kits-design.md`

## Global Constraints

- **Next.js:** antes de escrever código Next, leia o guia relevante em `node_modules/next/dist/docs/` (AGENTS.md). Rotas usam `export const dynamic = 'force-dynamic'`, e o `params` é `Promise<{ id: string }>`.
- **Funções SQL:**
  - `SECURITY DEFINER SET search_path = public`;
  - `RAISE EXCEPTION 'CODIGO'`;
  - `SELECT … FOR UPDATE` sempre filtrado por `clinic_id`;
  - `REVOKE ALL … FROM PUBLIC, anon, authenticated` e `GRANT EXECUTE … TO service_role`.
- **Migração:** `supabase/2026-11-10-kits.sql`, que pode ser rodada mais de uma vez, com cabeçalho no estilo de `supabase/2026-11-10-estoque.sql` ("Rode depois de supabase/2026-11-10-estoque.sql"). O conteúdo é acrescentado também ao fim de `supabase/schema.sql`.
- **Erros nas rotas:** `withClinic` vem de `@/lib/ia/rotas`; `respostaDeErro` e o tipo `Mapa` vêm de `@/lib/convenios/rotas`.
- **Quantidades:** inteiras de 1 a 9999. Kit ou baixa têm de 1 a 50 itens. Nome do kit: de 1 a 80 caracteres, sem espaços nas pontas.
- **Status de material:** `material_status` aceita `NULL`, `'pendente'`, `'baixado'` ou `'dispensado'`.
- **React:** a regra eslint react-hooks não permite `setState` síncrono no corpo de um effect. Busque os dados dentro do effect com uma variável de cancelamento, como em `src/app/(dashboard)/protese/page.tsx`.
- **Testes no Windows:** rode do PowerShell, com `Set-Location C:\Workspace\odontologia`, usando `npx vitest run <arquivo>`.
- **Textos:**
  - toda a interface em português;
  - botões "Dar baixa", "Agora não" e "Não usar material";
  - pergunta: "Este tratamento teve baixa de material. Devolver o material ao estoque?", com as respostas "Devolver", "Manter baixa" e "Cancelar";
  - etiquetas "Material pendente" e "Material baixado".
- **Commits:** terminam com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Devolver, baixar de novo e devolver outra vez:** a segunda devolução só pode devolver a segunda baixa. Nada pode ser devolvido duas vezes (Task 1, regra de "saídas ainda não devolvidas").
2. **Gravação pelo navegador com `material_status` no corpo**, por exemplo um update da ficha que mande `material_status: 'baixado'`: o gatilho ignora esse campo (Task 1, verificação ao vivo na Task 7).
3. **Baixa com um item sem saldo no meio da lista:** nada é baixado, a resposta é 409 com o nome do produto e o `itemId`, e a linha desse produto é marcada (Tasks 3 e 5).
4. **Evolução que conclui dois tratamentos:** as janelas abrem uma depois da outra, e "Agora não" passa para a próxima sem perder a segunda (Task 6).
5. **Procedimento com acento ou maiúsculas diferentes do nome do kit** ("RESTAURAÇÃO resina" e o kit "Restauracao Resina"): a sugestão encontra o kit (Task 2).

  - Caso contrário, aplica, nesta ordem, as regras da spec:
    1. num INSERT, os dois campos ficam nulos; num UPDATE, recebem os valores de OLD;
    2. se o tratamento acaba de ser concluído e o status de material está nulo, vira `pendente`;
    3. se deixou de estar concluído e o status era `pendente` ou `dispensado`, volta a nulo, com `material_kit_id` nulo.

- [ ] **Step 3: Escrever `create_inventory_kit` e `update_inventory_kit`.**
  - Validação antes de gravar:
    - o nome vem de `btrim(p_data->>'name')`;
    - `items` precisa ser um array com 1 a 50 elementos; senão, `KIT_VAZIO`;
    - quantidade inteira entre 1 e 9999; senão, `QUANTIDADE_INVALIDA`;
    - `item_id` repetido gera `ITEM_REPETIDO`;
    - todos os `item_id` precisam existir em `inventory_items` com `clinic_id = p_clinic_id`; senão, `PRODUTO_INVALIDO`.
  - `active` vem de `coalesce((p_data->>'active')::boolean, true)` na criação. Na edição, se a chave estiver ausente, mantém o valor atual.
  - A edição trava o kit com `FOR UPDATE` (`KIT_NAO_ENCONTRADO`), atualiza nome, `active` e `updated_at = now()`, apaga os itens e insere a lista nova.

- [ ] **Step 4: Escrever `treatment_material_apply`**, como descrito na spec:
  - erros, nesta ordem de checagem:
    - `TRATAMENTO_NAO_ENCONTRADO`
    - `TRATAMENTO_NAO_CONCLUIDO`
    - `MATERIAL_JA_RESOLVIDO`
    - `KIT_NAO_ENCONTRADO`
    - `KIT_VAZIO`
    - `QUANTIDADE_INVALIDA`
    - `ITEM_REPETIDO`
  - percorre os itens com `ORDER BY item_id`;
  - chama `inventory_exit(..., 'uso', NULL, left('Tratamento: ' || procedure, 200))` dentro de `BEGIN … EXCEPTION WHEN raise_exception THEN RAISE EXCEPTION '%:%', SQLERRM, v_item_id; END`;
  - em seguida faz `UPDATE inventory_movements SET treatment_id = p_treatment_id WHERE clinic_id = p_clinic_id AND item_id = v_item_id AND type = 'out' AND treatment_id IS NULL AND created_at = now()`;
  - no fim, chama `PERFORM set_config('app.material','on',true)`, atualiza `treatments` (`material_status='baixado'`, `material_kit_id=p_kit_id`) e chama `PERFORM set_config('app.material','off',true)`;
  - devolve `{"itens":[{"item_id","quantidade","lotes"}]}`, em que `lotes` é o array `lotes` que `inventory_exit` devolveu.

- [ ] **Step 5: Escrever `treatment_material_skip` e `treatment_material_return`.**
  - **Regra das saídas ainda não devolvidas** (lacuna da spec, decidida aqui): `return` só considera as saídas (`type='out'`) desse tratamento com `created_at` maior que a última devolução desse tratamento, isto é, `coalesce(max(created_at) das linhas type='in' AND kind='devolucao' com o mesmo treatment_id, '-infinity')`.
  - Para cada saída nesse conjunto, em ordem de `item_id`:
    - trava o produto;
    - se o produto controla validade e `lot_id` aponta para um lote que ainda existe, soma no lote;
    - se o produto controla validade e o lote não existe mais, insere um lote com `lot_code` NULL, `expires_at` NULL e essa quantidade;
    - se o produto não controla validade, soma direto em `quantity`.
  - Recalcula `inventory_items.quantity`: para produto com validade, a soma dos lotes.
  - Insere uma movimentação `in`, `devolucao`, com o lote, o `treatment_id` e a nota `left('Devolução: ' || procedure, 200)`.
  - No fim, com o mesmo par `set_config` on/off, grava `material_status = CASE WHEN status='completed' THEN 'pendente' ELSE NULL END` e `material_kit_id = NULL`.
  - Devolve `{"devolvidos": n}`.
